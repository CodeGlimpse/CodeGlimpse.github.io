# “游戏”栏目可行方案

结论：现有 Hugo + GitHub Pages 足以承载一个小型 HTML 游戏栏目。建议先以一款简单的 2D 单机游戏跑通完整流程，再扩展到三款；Hugo 负责介绍与导航，游戏使用独立静态资源包按需加载。

本文件仅为方案，未创建游戏栏目、页面、脚本、资源或安装依赖。内容与阅读导航已完成发布和线上验收后，才整理本建议。

## 首版范围

- 候选类型：记忆翻牌、贪吃蛇、2048 等规则清晰、适合键盘与触屏的小游戏。首款可优先选择素材需求较少的记忆翻牌。
- 提供游戏简介、操作说明、开始、暂停、重新开始、静音和本地最高分；按游戏实际需要裁剪控件。
- 使用自己维护的代码，或具有明确再分发许可的代码和素材，并保留署名与许可文件。
- 首版采用浏览器本地存档。账号、跨设备同步、在线对战和可信全球排行榜需要后端服务，属于后续独立范围。
- 原生 HTML/CSS/JavaScript 或 Canvas 2D 已足够；只有场景、动画、碰撞需求明显增加时，再评估 Phaser 等框架。

## 页面与资源分开

建议结构如下，尚未创建这些路径：

```text
content/zh-cn/games/_index.md             游戏目录
content/zh-cn/games/<id>/index.md         介绍、操作与试玩页
content/en/games/...                     对应英文页面
layouts/games/list.html                  游戏卡片目录
layouts/games/single.html                试玩页外壳
static/game-assets/<id>/<version>/       独立 HTML、JS、图片和音频
```

访客地址使用 `/games/`、`/games/<id>/` 和对应 `/en/` 路径。运行资源使用 `/game-assets/`，避免与 Hugo 生成的试玩页 `index.html` 冲突。

目录页只加载封面和说明；点击“开始游戏”后再建立 iframe、加载游戏资源和音频。游戏列表与工具注册表分别维护，文章首页及 RSS 继续只包含 `post`。封面、操作说明、输入方式、版本和许可是每款游戏的基础信息。

## 推荐的运行方式

| 方式 | 适用情况 | 需要注意 |
| --- | --- | --- |
| 同源 iframe，推荐用于首批本人维护的游戏 | 游戏与博客共用当前 Pages 部署 | 隔离样式和脚本全局变量，但不是安全隔离；仍共享同源存储和权限 |
| 独立域名或来源的 iframe | 以后引入第三方游戏，或需要更强隔离 | 需要另行配置托管、来源与消息协议；存档归属该来源 |
| 直接把游戏代码塞入文章正文 | 极小演示 | 容易与主题样式、快捷键和页面生命周期耦合，不作为栏目默认方式 |

同源 iframe 不应被称为“安全沙箱”。MDN 明确指出，同源内容同时获得 `allow-scripts` 和 `allow-same-origin` 时，可以使 sandbox 失去预期保护。未知来源 HTML 不应直接部署到博客同源目录。

如果以后采用不带 `allow-same-origin` 的沙箱，直接访问存储可能被限制，不能照搬同源 localStorage 存档。采用跨来源消息通信时，应核对发送来源和窗口、限制消息类型与大小，并验证数据结构；无需通信时就不增加消息接口。

## 存档、输入与资源预算

- 每款游戏使用独立的版本化存储键，例如 `cg-game:<id>:v1`，只保存分数、设置及必要进度，提供重置入口。存储不可用时仍应能游玩，并说明本次进度不能保存。
- 方向键和空格只在游戏获得焦点时处理；退出游戏后恢复正常页面操作。触屏控件应有足够点击面积，暂停或切换标签页时停止游戏循环和音频。
- 建议单款首屏资源以 **2 MB 以内**为初始预算，并以实际移动网络测试调整。这是项目目标，不是平台保证。封面和音频按需加载。
- GitHub 官方当前规定已发布 Pages 站点不超过 **1 GB**，并有 **100 GB/月的软带宽限制**。少量轻型游戏较合适，大型资源包需要重新评估托管和流量。
- 对大型 WebAssembly、多线程引擎导出包，应先验证内存、移动浏览器和跨来源隔离头等托管要求，再决定技术路线。

## 必须单独处理现有离线缓存

当前 [Service Worker](../static/sw.js) 会缓存成功的同源 GET 响应，而且没有按游戏限制容量。直接增加大型游戏包，会把这些资源一起写入博客缓存。

首版建议将 `/game-assets/` 排除在现有 Service Worker 的主动缓存范围外，使用正常 HTTP 缓存，并把离线游玩留到有明确需求时再做。以后如增加离线能力，应按游戏和版本管理缓存、设置容量/数量上限并清理旧版本，不能在安装博客缓存时预取全部游戏。

## 实施与验收顺序

1. **确认首款游戏及来源。** 确定规则、键盘/触屏操作、许可和本地存档需求。
2. **做一款完整试玩页。** 跑通目录入口、按需加载、开始/暂停/重开、存档和移动布局。
3. **验证与现有博客共存。** 覆盖焦点恢复、音频停止、存储拒绝、资源失败、缓存更新、双语说明和 RSS 不混入游戏。
4. **通过现有发布门禁后再上线。** 在 E2E 与线上巡检中加入该游戏的关键行为和资源；稳定后扩展到三款。

建议从这个范围开始，能够保留当前静态站点的部署方式，也便于之后独立更新或移除单款游戏。是否引入框架、第三方游戏或独立域名，应在具体需求出现时再决定。
